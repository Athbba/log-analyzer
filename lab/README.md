# Docker lab

A disposable SSH server and the clients that attack it, so the analyzer can be
tested on logs written by the real OpenSSH, PAM, sudo and shadow-utils rather
than only on the synthetic sample.

```sh
npm run lab            # build, play every scenario, write lab/out/auth.log, check it
npm run lab:fixture    # the same, but refresh the committed test/fixtures/lab/auth.log
node scripts/lab.js verify some.log --labels test/fixtures/lab/labels.json
```

Requires Docker with Compose v2. A run takes about a minute after the first
build.

## What runs

| Container | IP | Role |
|---|---|---|
| `target` (`lab-target`) | 172.30.0.10 | Debian 13, OpenSSH 10.0, rsyslog writing `/var/log/auth.log` |
| `office` | 172.30.0.20 | alice, bob and dave doing normal work |
| `attacker-guess` | 172.30.0.66 | dictionary attack on common account names |
| `attacker-breakin` | 172.30.0.77 | guesses `deploy`'s password, plants a sudo user |

Scenarios run one after another, in this order:

| Scenario | Script | Expected findings |
|---|---|---|
| admin work | [admin-work.sh](client/scenarios/admin-work.sh) | possible breach (low) ×2, account change (low, medium) |
| password guessing | [guessing.sh](client/scenarios/guessing.sh) | brute force (medium) |
| break-in + backdoor | [break-in.sh](client/scenarios/break-in.sh) | brute force, possible breach, account change, all high |

The expected findings are in [test/fixtures/lab/labels.json](../test/fixtures/lab/labels.json),
with a note on each. The second low possible breach in the admin work is a
real false positive the lab exposed: dave's key login comes two seconds after
bob's mistyped password from the same workstation, and the rule counts
failures from the IP for any username.

## Safety

The scenarios guess passwords, so they are fenced in three ways:

1. **No route out.** The lab network is `internal: true`: Docker gives it no
   gateway, so the containers can reach each other and nothing else.
2. **The scenarios check their target.** [lib.sh](client/scenarios/lib.sh)
   resolves `lab-target` and exits with status 64 unless it is on the lab
   subnet `172.30.0.0/24`. The host name is a constant, not an argument.
3. **The guard is tested on every run.** Before any scenario, `scripts/lab.js`
   starts a client with no network at all and requires it to refuse (exit 64).

The lab's users and passwords (`setup-users.sh`) exist only inside the
container. They are not secrets, and nothing in the lab should ever be
published on a port.

## Design notes

- **The lab clock reads 10:00.** A container can't set its own clock, but it
  can choose its timezone. `scripts/lab.js` sets a POSIX `TZ` (for example
  `LAB-10`) so that local time on the target is about 10:00 whenever the lab
  runs. Otherwise the unusual-hour rule would fire or not depending on when CI
  happened to run. rsyslog writes RFC 3339 timestamps with that offset, and
  the analyzer keeps the wall-clock time.
- **`PerSourcePenalties no`.** OpenSSH 9.8+ refuses connections for a while
  from addresses that keep failing to authenticate. That is a good defence on
  a real server and it does reduce brute-force volume, but in the lab it
  would make the scenarios depend on the penalty timer.
- **Login keys** are generated by the target on first start into a shared
  volume, so no private key is ever committed.
- **No systemd** in the container, so there are no `systemd-logind` lines.
  The synthetic sample covers those.
- Each run has different times, PIDs and ports, but must produce the same
  labelled incidents. CI runs the lab on every pull request and uploads the
  log as an artifact.
